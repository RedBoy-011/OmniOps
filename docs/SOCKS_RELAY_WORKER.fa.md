# مسیر SOCKS خصوصی از Master به Worker

در شبکهٔ فعلی، Master با IP خصوصی 172.19.30.100 به پراکسی 172.16.20.250:7890 می‌رسد، اما TLS مقصد از این مبدأ کامل نمی‌شود. همان TLS از Worker با IP 172.19.30.99 کامل می‌شود. رلهٔ TCP کم‌حجم روی Worker فقط از IP خصوصی Master اتصال می‌پذیرد و بایت‌ها را به همان پراکسی خصوصی می‌فرستد. درخواست Provider همچنان با SOCKS5h اجرا می‌شود، نام مقصد در پراکسی حل می‌شود و TLS مقصد تا سرویس Gemini برقرار می‌ماند.

روی Worker پس از به‌روزرسانی مخزن، از پوشهٔ آن به‌عنوان root اجرا کنید:

```bash
OMNIOPS_RELAY_MASTER_IP=172.19.30.100 OMNIOPS_RELAY_WORKER_IP=172.19.30.99 OMNIOPS_RELAY_PROXY_IP=172.16.20.250 bash scripts/install-socks-relay-worker.sh
```

سرویس با کاربر غیر root، سقف ۱۶ اتصال همزمان و محدودیت IP در سطح سرویس اجرا می‌شود؛ فقط روی IP خصوصی Worker و پورت TCP 17890 گوش می‌دهد. روی فایروال میان Worker و Master فقط دسترسی **172.19.30.100 → 172.19.30.99:17890/TCP** لازم است. این پورت را روی اینترنت باز نکنید. وضعیت: `systemctl status omniops-socks-relay.service`. در پنل Gemini گزینهٔ SOCKS را با نشانی `socks5h://172.19.30.99:17890` انتخاب کنید و «تست و دریافت مدل‌ها» را بزنید. قطع Worker یا پراکسی باعث خطای آشکار Provider می‌شود؛ مسیر مستقیم به‌صورت خودکار جایگزین نمی‌شود.

این رله برای شبکهٔ خصوصی فعلی است. در استقرار نهایی Edge/Overlay باید دسترسی دو گره به‌صورت مجزا محدود و پایش شود. پاسخ‌های مدل و کلید API داخل TLS مقصد باقی می‌مانند، ولی سرنام SOCKS در شبکهٔ خصوصی به سمت Worker انتقال پیدا می‌کند.
