# برنامهٔ اتصال MCP و ابزارهای اجرایی به OmniOps

این سند ۹ پیشنهاد پیوست کاربر را در معماری واقعی Master/Worker/Windows Agent جای می‌دهد. این‌ها اکنون در OmniOps نصب یا فعال نشده‌اند. اتصال هر سرور پس از بررسی نسخه، مجوز، مدل هزینه و آزمون واقعی اعلام می‌شود. مبنا: قرارداد MCP جاری با پیام‌های JSON-RPC، ابزار/منبع/پرامپت و transportهای پشتیبانی‌شده؛ API اختصاصی هر محصول جای قرارداد عمومی MCP را نمی‌گیرد.

## مرز معماری

```text
چت وب و ایجنت ویندوز -> Master: هویت، OmniRoute، سیاست داده، فهرست ابزار، ممیزی
                                      |
                         پیشنهاد مدل برای فراخوانی ابزار
                                      v
                       دروازهٔ قابلیت/محدوده/تأیید
                                      |
                      Worker ایزوله / ایجنت همان دستگاه
                                      |
                         MCP local stdio / remote HTTP
```

- Master فقط تنظیمات، سیاست، کار، نتیجهٔ محدودشده و سلامت connector را نگه می‌دارد. سرورهای پرمصرف MCP و مرورگر Headless روی Worker اجرا می‌شوند؛ ابزار مربوط به مرورگر شخصی روی ایجنت ویندوز همان کاربر اجرا می‌شود. خرابی ابزار نباید پنل و ورود Master را بخواباند.
- انتخاب مدل در OmniRoute و اختیار ابزار دو تصمیم جدا هستند. خروجی مدل، متن سایت، Issue گیت‌هاب یا پاسخ MCP دستور اجرایی معتبر نیستند. هر فراخوانی با هویت کاربر، پروفایل، دامنهٔ دستگاه/منبع، سیاست خروج داده، نوع عملیات و تأیید لازم دوباره کنترل می‌شود.
- سه سطح عملیات: مشاهدهٔ محدود؛ نوشتن/ارسال/تغییر قابل بازبینی؛ عملیات زیرساختی یا پرهزینه با تأیید مشخص شخص مجاز. تأیید مدیر یا کاربر همان دستگاه طبق پروفایل و نوع ابزار تعیین می‌شود؛ نتیجه، شناسهٔ کار و تصمیم در audit ثبت می‌شوند.
- متن، تصویر و لاگ دریافت‌شده از وب/مرورگر/ابزار با سقف حجم، پاک‌سازی رازها و برچسب منبع به مدل می‌رسند. سیاست `local_only` هم مدل ابری و هم MCP ابری را ممنوع می‌کند؛ درخواست کاربر برای یک مدل لوکال به‌تنهایی مجوز ارسال داده به ابزار اینترنتی نیست.
- Secretها به‌صورت مرجع در مخزن اسرار سرویس نگه‌داری و فقط هنگام اجرای مجاز به connector داده می‌شوند؛ PAT و AWS access key به متن چت، لاگ، Git یا SQLite بدون حفاظت سپرده نمی‌شوند. OAuth/App/نقش کوتاه‌مدت در صورت پشتیبانی محصول ارجح است.

## بررسی هر پیشنهاد

| ابزار | امکان/محل مناسب | دامنهٔ نخستین انتشار و شرط فعال‌سازی |
|---|---|---|
| Context7 | بله؛ connector اختیاری روی Worker یا HTTP بیرونی برای مستندات کدنویسی | فقط پروفایل برنامه‌نویسی و جست‌وجوی read-only، با کنترل خروج پرسش به بیرون. کد MCP متن‌باز است اما backend مستندات Context7 کامل در این مخزن منتشر نشده؛ حالت آفلاین مطلق ادعا نشود. |
| Chrome DevTools MCP | بله؛ ماژول اختیاری ایجنت ویندوز در نشست کاربر | فقط پس از فعال‌سازی کاربر، اتصال به مرورگر/تب مشخص، آغاز با کنسول و DOM خواندنی؛ محتوای حساس پیش از ارسال به Master پالایش شود. پنل سرور نباید خودکار به Chrome خانگی دسترسی داشته باشد. |
| Playwright MCP | بله؛ مرورگر مجزای Worker برای آزمون/اتوماسیون، نه جای Chrome شخصی | محیط جدا، دامنه و زمان مجاز، لاگین و دانلود/ارسال با تأیید متناسب با پروفایل؛ هر اجرا دارای job و گزارش مستقل. |
| GitHub MCP Server | بله؛ اتصال OAuth/GitHub App یا توکن محدود | نخست خواندن repo/Issue؛ ایجاد branch/commit/PR یا Push تنها در محدودهٔ مخزن مجاز و پس از بازبینی و تأیید. هیچ PAT عمومی/نامحدود در SQLite خام ذخیره نشود. |
| n8n MCP | بله؛ n8n روی Worker اتوماسیون | از قابلیت MCP رسمی n8n و تنها Workflowهایی استفاده شود که برای MCP به‌صراحت فعال شده‌اند؛ مشاهده ابتدا، اجرای workflow دارای پیام/انتشار پس از تأیید. «همهٔ نودها و همهٔ workflowها» خودکار در دسترس نیستند. |
| Framelink Figma MCP | بله؛ connector خواندنی در Worker توسعه | توکن و فایل/پروژهٔ مجاز، خواندن ساختار/استایل، سپس تولید کد و آزمون بصری؛ خروجی Pixel-perfect تضمین نمی‌شود. |
| AWS MCP Servers | بله؛ اختیاری پس از وجود حساب AWS سازمان | برای مشاهده ابتدا ابزارهای انتخاب‌شده؛ عملیات تغییر EC2/IAM/S3 با نقش محدود و تأیید مجزا. سرویس روی Worker مدیریت اجرا شود، نه Shell آزاد Master. |
| Firecrawl MCP | بله؛ connector وب بیرونی/نصب خودمیزبانِ تأییدشده | جست‌وجو و استخراج لینک‌های مجاز با محدودیت دامنه، حجم و هزینه؛ محتوای اسناد محرمانه بدون اجازه به سرویس بیرونی ارسال نشود. خطای صفحهٔ پویا صریح گزارش شود. |
| Apify MCP | بله؛ connector ابری اختیاری | Actorهای انتخاب‌شده و سقف هزینه، مجوز دامنه/داده، job قابل پیگیری و خروجی صفحه‌بندی‌شده؛ اجرای بی‌قیدِ Actorهای کشف‌شده مجاز نیست. |

Chrome DevTools و Playwright هم‌پوشانی دارند، اما اولی برای دیباگ مرورگر فعلی کاربر و دومی برای اجرای وب در محیط ایزولهٔ Worker است. Firecrawl و Apify هر دو برای وب‌اند؛ تا روشن‌شدن نیاز و هزینهٔ واقعی، همزمان به‌عنوان پیش‌نیاز نسخهٔ اول نصب نمی‌شوند.

## قرارداد هسته و پنل

- رجیستری شامل connector_id، منبع/نسخهٔ pinned، مالک سازمانی، محل اجرا، transport، ابزارهای فهرست‌شده با schema، سطح دسترسی، قواعد تأیید، شبکهٔ مجاز، سقف زمان/خروجی/هزینه و وضعیت آزمون است. ورود صرف یک URL یا نام package ابزارها را فعال نمی‌کند.
- در پنل Admin کارت هر connector: `تعریف نشده / آزمایشی / فعال / خراب / غیرفعال`، آخرین سلامت، فهرست ابزارها و دامنهٔ دسترسی، گزینهٔ تست read-only، سقف هزینه و لاگ آخرین فراخوانی. اتصال HTTP بیرونی فقط در حالت دادهٔ مجاز و با مسیر direct/SOCKS انتخاب‌شدهٔ Provider همان ابزار انجام شود.
- در چت وب و ایجنت، کاربر ابزار یا مهارت مجاز را دستی انتخاب می‌کند یا حالت «پیشنهاد هوشمند» را فعال می‌کند؛ قبل از عملیات مؤثر، نام ابزار، آرگومان‌های قابل فهم، مقصد داده و هزینه/اثر به تأییدکنندهٔ مجاز نمایش داده می‌شود. مدل می‌تواند ابزار مناسب را پیشنهاد دهد؛ پس از قطع connector، مکالمه می‌تواند بدون آن ادامه یابد و خطا پنهان نشود.
- هر پاسخ ابزار دارای منشأ، وضعیت و زمان اجراست. ورودی طبق JSON Schema اعتبارسنجی می‌شود، پاسخ از نظر حجم/ساختار محدود و نتیجهٔ نامطمئن به‌صورت داده به مدل تحویل می‌شود؛ دستورالعمل‌های جاسازی‌شده در صفحات وب به مجوز تبدیل نمی‌شوند.

## ترتیب اجرا و معیار پذیرش

1. پس از آماده‌شدن مسیر پایدار مدل و Worker، `MCP Broker` مرکزی با رجیستری، policy، تأیید، audit و اجرا روی Worker جدا ساخته شود. ابتدا یک ابزار ساختگی read-only و یک ابزار نوشتنی با تست رد/تأیید، قطع Worker و خروج داده آزمایش شوند؛ صرف فعال‌کردن پکیج‌های بیرونی معیار پایان نیست.
2. pilot کاربردی: Context7 برای توسعه و GitHub فقط read-only، سپس n8n با یک workflow آزمایشی که مدیر فعال کرده است. در هر سه حالت پروفایل فاقد مجوز باید پاسخ 403 بگیرد و مدل نتواند با نوشتن دستور در متن صفحه سطح دسترسی را بالا ببرد.
3. ابزارهای مرورگر: Chrome DevTools روی همان دستگاه ویندوز با رضایت کاربر؛ Playwright مجزا در Worker با profile ایزوله. ثبت/ورود و هر کار دارای اثر جانبی با جریان تأیید عملی آزموده شود.
4. Figma و سپس AWS بسته به نیاز سازمان؛ Firecrawl و Apify به‌صورت انتخابی بر اساس استفاده، حریم داده و هزینه اضافه شوند. شمار ابزارها در رجیستری و دسترسی کاربر باید قابل کنترل باشد.
5. هنگام افزودن Edge عمومی، فقط transport و سرویس‌هایی که احراز هویت، TLS، محدودیت دسترسی و آزمون قطع/بازیابی دارند فعال شوند. هیچ MCP داخلی با پورت آزاد اینترنت عمومی منتشر نشود.

درصد پیشرفت محصول با این سند تغییر نمی‌کند؛ تنها پیاده‌سازی واقعی و آزمون پذیرش می‌تواند آن را بالا ببرد.
