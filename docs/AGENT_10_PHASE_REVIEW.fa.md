# تطبیق نقشهٔ ده‌فازی عامل با OmniOps

تاریخ بازنگری: ۳ اکتبر ۲۰۲۶. این سند نقشهٔ ده‌فازی پیشنهادی کاربر را با محصول یک‌سازمانی و حدود ۱۰ مدیر و مخزن جاری تطبیق می‌دهد؛ دروازهٔ توسعه و برآورد در [نقشهٔ پیشرفت](PROGRESS_ROADMAP.fa.md) ثبت است. **صرف وجود یک مسیر API به معنی آماده‌بودن تجربهٔ کاربری یا ابزار اجرایی نیست.**

## تطبیق مرحله به مرحله

| فاز پیشنهادی | شاهد فعلی | تصمیم و شرط پذیرش |
|---|---|---|
| ۱. چت ساده | درگاه مدل محلی/بیرونی، انتخاب مدل و ذخیرهٔ اختیاری تاریخچه وجود دارد؛ SSE/WS برای پاسخ، System Prompt قابل مدیریت، ثبت مصرف واقعی و سهمیهٔ توکن آماده نیست. | چت وب و ایجنت روی HTTPS با مدیر/عضو پذیرفته شود؛ streaming پاسخ و رویداد خطا/لغو، نسخه‌بندی Prompt سازمانی، توکن/هزینهٔ واقعی یا برآورد برچسب‌دار و سقف هر پروفایل اضافه شود. Prompt سازمانی از کاربر عادی یا فایل دریافت نشود. |
| ۲. پنج ابزار پایه | ابزارهای list_files، read_file، apply_patch، run_command، git_diff در OmniOps اجراگر ندارند. | هر ابزار قرارداد ورودی/خروجی، اعتبارسنجی سرور، محدودیت زمان و حجم پاسخ، مسیر واقعی بدون فرار symlink و شناسهٔ مجوز داشته باشد. ابتدا فهرست/خواندن و git_diff؛ نوشتن و Shell بعد از مرز اجرا و Approval. |
| ۳. حلقهٔ عامل | پیش‌نویس وظیفهٔ پایدار وجود دارد ولی اجرای ابزار، رویداد مراحل و Agent Loop وجود ندارد. | Harness در Master شناسهٔ کار، قدم، مدل، Tool Call و audit نگه دارد؛ سقف دور/زمان/هزینه، لغو قابل مشاهده و تشخیص درخواست تکراری را اعمال کند. آزمایش نخست با ابزار شبیه‌سازی‌شده و خواندنی. |
| ۴. Sandbox | Worker جدای مدل وجود دارد اما اجرای کد کاربر داخل sandbox پیاده نشده است. | قرارداد sandbox و Permission از **آغاز فاز ابزار** تعریف شود؛ پیش از run_command/apply_patch واقعی، اجراگر محصور لازم است. Docker روی Worker لینوکسی گزینهٔ اولیهٔ کار روی نسخهٔ منتخب پروژه است؛ دسترسی کنترل ویندوز از مسیر broker محدود ایجنت و رضایت کاربر، جدا از آن. Snapshot با محدودیت نگهداری، شبکهٔ بسته، کاربر غیرمدیر و حد منابع آزمون شود. |
| ۵. ویرایش امن کد | فایل پروژه در ایجنت به‌عنوان workspace انتخاب/ویرایش نمی‌شود؛ پیوست خصوصی فقط در Master ذخیره است. | اعمال patch در نسخهٔ منتخب پروژه، diff قبل/بعد، تغییرات موجود کاربر، بازگشت فقط برای تغییر محلی، تست مرتبط و artifact نتیجه؛ Undo عملیات خارجی مثل push یا ارسال پیام را برنمی‌گرداند. |
| ۶. امنیت و Approval | مجوزهای حساب و گره و اتصال TLS خصوصی وجود دارد؛ طبقه‌بندی مستقل ابزار و تأیید مرحله‌ای هنوز نیست. | READ_ONLY، LOCAL_WRITE، NETWORK_ACCESS، EXTERNAL_ACTION، DESTRUCTIVE در **مرز ابزار از روز اول** اعمال شوند. قواعد سرور/ایجنت بر اساس پروفایل و ابزار؛ تأیید محتوا، هدف، محدوده و مدت اعتبار را ثبت کند. انجام خارجی/حذف با تصمیم مستقل؛ دسترسی raw root از مدل ممنوع. |
| ۷. Skills و MCP | مستندات و طرح اتصال وجود دارد، registry و ابزار اجرایی پذیرفته‌شده وجود ندارد. | پس از آزمون sandbox و سیاست ابزار، مهارت نسخه‌دار و بازبینی‌شده به Harness متصل شود؛ MCP credential را در سرویس قابل اعتماد نگه دارد و هر فراخوانی به موتور مجوز خودی برگردد. نصب خودکار مهارت دلخواه از وب پیش‌فرض نباشد. |
| ۸. حافظه و Context | تاریخچهٔ اختیاری حساب و یادداشت شخصی وجود دارد؛ یادداشت‌ها فعلاً به مدل داده نمی‌شوند. | Turn/Session/Long-term با مالک و رضایت جداگانه، خلاصه‌سازی و بازیابیِ قابل مشاهده و حذف از ایندکس؛ جلوگیری از اشتراک اتفاقی زمینه بین حساب‌ها و پروژه‌ها. |
| ۹. رابط حرفه‌ای | پنل فارسی و ایجنت شناور ساخته شده‌اند؛ پروژه/پیش‌نویس و انتخاب مدل هست ولی نمایش Tool Call، Diff/Undo، terminal محدود، streaming و بودجه زنده نیست. | در هر فاز رابط همان قابلیت واقعاً کارا را نشان دهد؛ نمایش زیبا نباید جایگزین اجرای قابل آزمون شود. Web اجازهٔ مستقیم فایل/سیستم دستگاه ندارد. |
| ۱۰. کیفیت و Production | تست‌های Python، وب و CI Windows، TLS خصوصی و ثبت پورت/نصب‌کننده وجود دارد؛ Eval عامل، trace اجرا، سنجهٔ موفقیت و نسخهٔ عمومی پذیرفته نشده‌اند. | از فاز Agent Loop نمونهٔ ثابت Eval، tracing با پالایش راز، quota، retry کنترل‌شده، نرخ خطا/تأخیر و توقف/بازیابی؛ در پایان نصب پاک و آزمون بازیابی. |

## سه ایراد ترتیبی که نقشه باید رفع کند

۱. اگر فاز ۲ پنج ابزار را با Shell/نوشتن واقعاً منتشر کند و فاز ۴ تازه sandbox بیاورد، بازهٔ ناامن ایجاد می‌شود. schema، policy، harness و sandbox در طراحی از آغاز مشترک‌اند؛ حلقهٔ عامل ابتدا روی mock/read-only آزموده می‌شود و اجرای پراثر بعد از کنترل اجرایی فعال می‌گردد. Tool Call پیشنهاد مدل است و سرور باید هر بار مجوز را بررسی کند.
۲. Docker روی Worker لینوکسی جای Windows API و restart سرویس دستگاه را نمی‌گیرد. فایل‌های کاربر صرفاً با انتخاب پوشه و رضایت مشخص به نسخهٔ محدود کار منتقل یا در ایجنت مدیریت می‌شوند؛ Mount نوشتنی روی پوشهٔ اصلی اثر مستقیم روی میزبان دارد. برای اقدام ویندوزی broker با ابزار allowlist و تأیید جدا لازم است. Container بدون limit و تنظیم شبکه، sandbox مطمئن فرض نشود.
۳. بازگشت patch/commit محلی را باید از اقدام بیرونی (push، ایمیل، خرید، حذف داده) جدا کرد. approval باید پیش از اثر بیرونی و با شرح آن انجام شود؛ «بعداً Undo می‌کنیم» جای آن را نمی‌گیرد. از روز اول log پالایش‌شده و آزمون تزریق prompt لازم است.

## انتخاب فناوری مطابق نصب فعلی

| لایه | تصمیم برای برش فعلی | محرک بازنگری |
|---|---|---|
| رابط | Tauri + React ویندوز، React وب؛ حفظ پیاده‌سازی موجود | نیاز اثبات‌شده به قابلیتی خارج از Tauri، پس از آزمون نصب. |
| Harness و Gateway | Python Master موجود با Task API/اجرای محدود؛ Rust در ایجنت | مهاجرت Node/TypeScript تنها با دلیل عملی، برنامهٔ داده و آزمون سازگاری. Agents SDK/Responses/Agents API وابستگی اجباری نیستند؛ هسته باید با Ollama و Providerهای منتخب مستقل بماند. |
| Streaming | نمونهٔ SSE از Master به کلاینت، لغو و Event ID؛ برای ارتباط دوطرفهٔ دستگاه فقط در صورت نیاز WebSocket | نیاز اثبات‌شده به کانال هم‌زمان دوجهته و آزمون قطع/ازسرگیری. |
| داده | SQLite فعلی برای یک سازمان، تراکنش و پشتیبان؛ دادهٔ وظیفه و trace با مالک و سیاست نگهداری | PostgreSQL پس از سنجش قفل، هم‌زمانی، HA یا چندسازمانی؛ Redis/queue پس از نیاز واقعی به workerهای مستقل و job durable. |
| Sandbox | Docker/daemon محصور روی Worker مخصوص اجرای کد و پروژه، منابع محدود و شبکهٔ بسته؛ broker محدود Windows برای عملیات دستگاه | نیاز عملی به جداسازی قوی‌تر و بودجهٔ عملیاتی Firecracker/VM؛ Docker socket و کلیدهای Master نباید به مدل یا محیط اجرا داده شوند. |
| اتصال و مشاهده‌پذیری | ابزارهای داخلی با contract ثابت؛ MCP بعد از policy؛ رویداد/audit موجود و سپس OpenTelemetry | مسیر trace پایدار و نیاز مانیتورینگ چند سرویس؛ ورود APIهای بیرونی تنها با سیاست داده و رضایت. |
| احراز هویت | OTP و نشست حساب فعلی؛ OAuth/OIDC فقط وقتی SSO سازمانی واقعاً خواسته شود | پذیرش هویت سازمانی و طراحی مهاجرت/بازیابی. |

برای پایلوت عامل کدنویس، **یک مدل مجاز و یک پروژهٔ نمونه** کافی است؛ Providerها، SOCKS و Ollama موجود حذف یا غیرفعال نمی‌شوند. یک عامل و پنج ابزار با قابلیت‌های خواندنیِ اولیه معیار پذیرش‌اند، نه تعهد به قفل‌کردن کل محصول روی یک مدل. موتور دانش Khoj و Edge مطابق نقشهٔ پیشین اختیاری و مرحله‌ای باقی می‌مانند.
